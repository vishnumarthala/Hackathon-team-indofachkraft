# Translating DoctorNearMe (i18n)

Ticket 018. The UI speaks English (`en`), Hindi (`hi`) and Telugu (`te`). There is no i18n library: a small
typed `t()` over JSON catalogues. **Every new UI string in later tickets goes through `t()`** — visible text,
`aria-label`, `title`, `placeholder`, validation messages and page metadata.

## Where things live

| File | What |
|------|------|
| `messages/en.json` | Source of truth. Nested JSON grouped by surface (`common`, `language`, `nav`, `footer`, `banner`, `errors`, `login`, `landing`, `bookDemo`, `intake`, ...). |
| `messages/hi.json`, `messages/te.json` | Same keys, translated. |
| `messages/REVIEW.md` | Human review list (generated, see below). |
| `lib/i18n/config.ts` | `LOCALES`, `Locale`, `DEFAULT_LOCALE`, `LOCALE_LABELS`, `HTML_LANG`, `DEFAULT_TIME_ZONE`, `isLocale`, `isValidTimeZone`, cookie names. Safe anywhere. |
| `lib/i18n/server.ts` | `getLocale()`, `getTimeZone()`, `getT(namespace?)`, `getFormatter()`. Server Components, Route Handlers, server utilities. |
| `lib/i18n/client.tsx` | `useT(namespace?)`, `useLocale()`, `useTimeZone()`, `useFormatter()`, `I18nProvider`. Client Components. |
| `lib/i18n/format.ts` | `formatDate`, `formatDateTime`, `formatTime`, `formatNumber`, `formatInr`, `createFormatter`. Pure. |
| `lib/i18n/keys.ts` | `MessageKey`, `Namespace`, `TFunction` types derived from `en.json`. |

`lib/i18n/messages.ts` imports every catalogue: import it only from server code. The root layout passes
**only the active locale's** catalogue to `I18nProvider`, so the browser never receives another language.

## Using it

Server Component (or `generateMetadata`):

```tsx
import { getFormatter, getT } from "@/lib/i18n/server";

export default async function Page() {
  const t = await getT("login");               // keys relative to "login"
  const format = await getFormatter();          // viewer's locale + time zone
  return <h1>{t("title")}</h1>;                 // format.dateTime(row.created_at), format.inr(150000)
}
```

Client Component:

```tsx
"use client";
import { useFormatter, useT } from "@/lib/i18n/client";

export function Thing() {
  const t = useT("intake");
  const format = useFormatter();
  return <button aria-label={t("end")}>{t("start")}</button>;
}
```

Without a namespace use full keys: `(await getT())("nav.signIn")`. Unknown keys are a **type error**
(`t("unknown.key")` does not compile). Tests that render client components wrap them with
`withI18n(element, locale?)` from `tests/helpers/i18n.ts`.

Pure helpers that must stay testable without React (e.g. `startIntakeCall`) keep English defaults and take
an optional translated messages object built from `t` (see `intakeMessages(t)` in
`components/intake/IntakeCall.tsx`). API responses stay English; the client maps known statuses to
translated messages.

## Adding a key

1. Add it to `messages/en.json` under the surface it belongs to. Names are camelCase leaf keys inside the
   surface (`bookDemo.form.emailHint`); headlines with an emphasised part use `title` + `titleEm`.
2. Add the same key to `hi.json` and `te.json` (draft translation; keep placeholders identical).
3. Run `npx tsx scripts/i18n-review.ts` to update `messages/REVIEW.md`.
4. `npx vitest run tests/i18n-keys.test.ts` checks: identical key sets, identical `{placeholders}`, complete
   plural pairs, copy rules, product names kept, and that `REVIEW.md` lists every key with the current text.

## Interpolation and plurals

- Placeholders are `{name}`: `t("intake.title", { child: "Ravi" })`. Numbers are formatted with Indian
  grouping and Latin digits. A missing variable renders `{name}` literally and warns outside production.
- Plurals: define `key_one` and `key_other` (add `_zero`/`_two`/`_few`/`_many` only if a language needs it),
  then call the base key with `count`: `t("landing.features.fromConfirmed", { count: 38 })`. The form is
  chosen with `Intl.PluralRules` for the active locale (`hi` treats 0 and 1 as `one`).
- A key missing in `hi`/`te` falls back to English (one console warning per key outside production). The
  key test fails CI before that can ship.

## Dates, times, numbers, money

- The viewer's time zone comes from the browser: `components/TimeZoneSync.tsx` posts it once to
  `POST /api/locale` (`{ time_zone }`, cookie `dnm_tz`, saved on the profile when signed in) and refreshes.
  Fallback `Asia/Kolkata`. Store `timestamptz` (UTC); convert only for display.
- Use `getFormatter()` / `useFormatter()` (or the functions in `format.ts` with an explicit `timeZone`):
  `date(d, "short" | "long")` -> `13 Nov 2026`, `dateTime(d)` -> `13 Nov 2026, 1:30 am IST`,
  `time(d)` -> `1:30 am IST`, `number(n)` -> `12,34,567.5`, `inr(paise)` -> `₹1,50,000`.
- Times always include the zone abbreviation so a clinic time is never ambiguous. When a later ticket shows a
  clinic's local time next to the viewer's, format both with their own zone.
- Digits stay Latin (`numberingSystem: "latn"`) in every locale.

## Locale resolution

`getLocale()`: cookie `dnm_locale` -> signed-in `user_profiles.preferred_locale` -> on `/intake/<token>` the
case `language` -> `Accept-Language` (`hi*`, `te*`, `en*`) -> `en`. Anonymous requests never call Supabase;
signed-in requests read `user_profiles` at most once per request and only when a cookie is missing. The
language switcher (`components/LanguageSwitcher.tsx`, in the app header, landing nav, `/login`,
`/book-demo` and the intake page header) posts `{ locale }` to `/api/locale` and calls `router.refresh()`.
There are no `/[lang]` routes and no locale redirects in `proxy.ts`.

The **intake call language** (`Call language` select) is separate from the UI language: it defaults to the
case language (or the UI locale when a case has none) and switching the UI never changes it.

## What is not translated

- Clinical instrument content: ISAA item texts (`lib/isaa.ts`, `schemas/isaa.json`) and any quote of them
  in the UI (mark with `lang="en"`). They need clinically reviewed translations (risk 1).
- AI output and user content: briefs, reports, transcripts, prompts (`prompts/**`), messages, notes.
- Names: product `DoctorNearMe`, engine `CareThread`, `ISAA`, `ElevenLabs`, `Google Gemini`, `WhatsApp`
  stay in Latin script (checked by the key test).
- API error bodies (contract for clients and tests).

## Copy rules (all languages)

- No word for "diagnose"/"diagnosis" except "not a diagnosis" (`निदान नहीं` / `నిర్ధారణ కాదు`). In Telugu
  use `ధృవీకరించు` for "confirm", never `నిర్ధారణ`.
- Never "HIPAA compliant".
- Keep sentences short and plain; parents read these on a phone.
- Do not use `tracking-*` letter-spacing for meaning: it is switched off for Hindi and Telugu
  (`app/globals.css`) because it breaks Indic glyph shaping.

## Review workflow

Hindi and Telugu strings are drafted by the engineer or agent who adds the key and are **not** clinically or
natively reviewed. `messages/REVIEW.md` lists every key (key, en, hi, te, reviewer, status). A fluent
reviewer sets `reviewer` and `status` (`pending` | `approved` | `changes-requested`). Regenerating the file
keeps a row's status only while its hi/te text is unchanged. All rows must be `approved` before the
Hyderabad pilot launch.
